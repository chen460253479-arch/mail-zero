# 邮件关键字立即提交与反向撤销设计

## 背景

Zero Mail 当前对已读、重要和星标采用“先更新前端，等待五秒撤销窗口结束后再请求后端”的方式。用户在撤销窗口内刷新或关闭页面时，尚未执行的后端请求会丢失，重新加载后只能读到数据库中的旧状态。

## 目标行为

- 点击已读、重要或星标后，前端立即显示目标状态，并立即向后端提交对应关键字变更。
- 五秒撤销窗口继续保留，但不再控制主请求的执行时机。
- 用户点击撤销时，前端立即恢复原显示，并向后端提交目标状态相反的关键字变更。
- 页面在主请求完成后刷新时，从数据库读取到新状态，不再依赖前端内存中的乐观状态。
- 不改变文件夹、归档、标签、删除、暂停和草稿删除操作的现有执行方式。

## 数据流

### 正常提交

1. 前端记录乐观状态。
2. 立即调用 `mail.action.updateThreads`，写入 `$seen`、`$important` 或 `$flagged` 的目标状态。
3. 五秒撤销窗口内继续保留乐观状态，避免缓存刷新造成界面闪回。
4. 撤销窗口结束后刷新线程列表、线程详情和邮箱统计，再清理乐观状态。

### 撤销提交

1. 用户点击撤销后，立即移除本次乐观状态，恢复缓存中的原显示。
2. 如果主请求仍在执行，等待主请求结束。
3. 只有主请求成功时，才提交目标状态相反的关键字变更。
4. 反向请求结束后刷新线程列表、线程详情和邮箱统计。

## 并发与顺序

同一账户、同一关键字涉及的操作必须按触发顺序执行。主请求和反向撤销请求进入同一关键字操作队列，防止连续点击或网络响应乱序导致较早的请求覆盖较新的用户状态。

不同关键字之间不互相阻塞，例如星标请求不需要等待重要请求。不同账户之间也不共享队列。

## 错误处理

### 主请求失败

- 立即清理乐观状态。
- 不发送反向请求，因为数据库没有完成正向变更。
- 刷新真实数据并显示操作失败提示。

### 反向请求失败

- 刷新真实数据，使界面恢复为数据库实际保存的正向状态。
- 显示操作失败提示，不伪造撤销成功。

### 页面刷新

主请求在点击时已经开始，不再依赖 Toast 自动关闭回调。浏览器刷新会清空前端撤销能力，但已经完成的后端写入仍然保留。刷新发生在网络请求尚未送达服务器的极短窗口时，仍受浏览器中断未完成请求的行为限制。

## 实现边界

- 保留 Server API 和 Mail Core 的现有关键字写入契约。
- 关键字操作仍不传递 `ifInState`，因为它们表达的是幂等的目标状态。
- 保留五秒撤销时长。
- 不修改 PostgreSQL 表结构或已有邮件数据。
- 不引入持久化前端操作队列、Service Worker 或新的依赖。

## 测试

- 验证创建操作时立即执行主请求，而不是等待撤销窗口结束。
- 验证主请求成功后点击撤销会执行一次反向请求。
- 验证主请求尚未完成时点击撤销，会在主请求完成后再执行反向请求。
- 验证主请求失败时不会执行反向请求，并触发失败回滚。
- 验证同一关键字的连续操作按触发顺序执行。
- 运行 Mail 全量测试和生产构建。
