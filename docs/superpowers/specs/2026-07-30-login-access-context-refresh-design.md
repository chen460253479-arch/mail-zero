# 登录后访问上下文刷新设计

## 背景

管理员密码登录接口能够成功创建会话，浏览器也能保存并携带
`better-auth.session_token`。但是登录页通过 React Router 的客户端
`navigate('/mail/inbox')` 进入邮件页面时，根加载器不会重新运行。

用户打开登录页时，根加载器已经把应用访问上下文解析为
`anonymous`。登录后的 SPA 导航继续复用这个旧上下文，因此
`MailLayout` 即使面对有效会话，仍会把用户重定向回 `/login`。

## 目标

- 登录成功后重新创建根访问上下文。
- 保留邮件页面的匿名访问检查和基于用户 ID 的缓存隔离。
- 不改变登录接口、Cookie、会话存储或 CRM Launch 登录流程。
- 不引入额外的历史数据迁移。

## 方案

密码登录成功后不再使用 SPA `navigate`，改为同站完整页面跳转到
`/mail/inbox`。

完整跳转会重新加载应用，使根加载器携带新会话再次执行。根加载器
随后产生 `mode: 'user'` 和对应的 `user:<userId>` 缓存主体，邮件布局
即可在正确的用户访问上下文中渲染。

登录失败或请求异常时仍停留在登录页并显示现有错误信息。只有成功
登录才触发完整跳转。

## 数据流

1. 用户在 `/login` 提交管理员邮箱或普通用户名及密码。
2. Zero Server 创建 Better Auth Session，并向浏览器设置会话 Cookie。
3. 前端确认登录响应成功。
4. 浏览器完整跳转到 `/mail/inbox`。
5. 根加载器携带会话 Cookie 查询 Session。
6. 根加载器按 Session 用户 ID 建立用户访问上下文和缓存主体。
7. 邮件布局通过匿名检查并展示该用户可访问的数据。

## 测试与验收

- 增加登录导航回归测试，证明登录成功采用完整页面跳转，而不是
  React Router SPA 导航。
- 保留登录失败不跳转的行为测试。
- 运行邮件前端定向测试和类型检查。
- 使用隔离浏览器验证登录后最终地址为 `/mail/inbox`，并且
  `get-session` 返回有效用户。
- 不自动执行 Docker 构建、打包或容器重启；如需运行容器验证，只
  提供手动命令。
