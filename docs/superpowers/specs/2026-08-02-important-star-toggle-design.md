# 重要与星标切换修复设计

## 背景

Zero Mail 的重要与星标切换同时存在两个问题：

1. 前端在撤销窗口内使用乐观状态更新工具栏和列表，但详情邮件标签仍读取接口缓存中的原始 `tags`，导致同一页面显示互相矛盾。
2. 关键字写入在撤销窗口结束后才执行，却携带渲染时缓存的 `mailboxState`。账户状态在此期间发生变化时会触发 `STATE_MISMATCH`，数据库写入被回滚。

## 目标行为

- 点击取消重要或取消星标后，列表、详情工具栏和详情标签立即显示一致的乐观结果。
- 撤销操作时不向后端写入，并恢复原始显示。
- 后端写入成功后刷新线程列表、线程详情和邮箱统计，再清理乐观状态。
- 后端写入失败时清理乐观状态、刷新真实数据并提示失败。
- 重要与星标操作最终分别删除或添加 `$important`、`$flagged`。

## 设计

### 关键字写入

前端的已读、重要和星标都通过同一个幂等关键字操作入口执行。该入口不再传递从 `Mailbox/get` 缓存获得的 `ifInState`。这些操作表达的是明确的最终状态（添加或删除某个关键字），可以安全地在 Mail Core 当前事务状态上执行。

`ifInState` 仍保留在 Server API 和 Mail Core 中，供需要显式比较并交换语义的 API 客户端使用。本次不改变后端契约和数据库模型。

### 详情乐观显示

新增一个纯函数，把线程级 `optimisticImportant` 和 `optimisticStarred` 投影到每封详情邮件的关键字标签：

- `true`：确保存在对应的 `IMPORTANT` 或 `STARRED` 标签；
- `false`：移除对应标签；
- `null`：保持接口返回的原始标签。

线程操作会更新线程内全部邮件，因此投影同样作用于线程中的全部消息。该函数只改变用于渲染的副本，不修改查询缓存中的原始 DTO。

## 错误处理

- 保留现有失败回滚和查询刷新行为。
- 保留 Server 对真实 `STATE_MISMATCH` 的 `409 CONFLICT` 映射。
- 不增加自动重试、全局操作队列或新的状态管理层。

## 测试

- 单元测试证明重要和星标的乐观 `true/false/null` 投影正确。
- 单元测试证明关键字操作输入在未提供状态时不会生成 `ifInState`。
- 运行相关 Mail 单元测试、Server Mail API 单元测试以及 Mail/Server 生产构建。

## 非目标

- 不修改文件夹、标签和移动操作的并发策略。
- 不修改数据库结构或已有邮件数据。
- 不改变撤销窗口的交互时长。
